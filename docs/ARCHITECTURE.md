# Архитектура решения

## Обзор

```
 Браузер (SPA, vanilla JS)  ──HTTP/JSON──►  FastAPI (app/api/routes.py)
                                               │
                         ┌─────────────────────┼──────────────────────────┐
                         ▼                     ▼                          ▼
              services/inventory.py   services/logs.py         services/maintenance.py
              установка/снятие/        разбор журналов,         регламенты, остатки,
              перестановка             дедупликация, начисление список работ, выполнение
                         └──────────► services/usage.py ◄────────────────┘
                                      расчёт наработки (SQL)
                                               │
                                     SQLAlchemy 2 ORM → SQLite / PostgreSQL
```

* **Бэкенд** — FastAPI + SQLAlchemy 2. Бизнес-логика в `app/services/*`, HTTP-слой тонкий.
  Каждый изменяющий запрос — одна транзакция; нарушение бизнес-правила → `DomainError` → HTTP 4xx
  с понятным сообщением на русском.
* **Фронтенд** — одностраничное приложение без сборки и без внешних CDN (`app/static`),
  раздаётся тем же сервером. Работает в закрытом контуре, где нет интернета.
* **Хранилище** — SQLite по умолчанию (ноль настройки), любая СУБД SQLAlchemy через
  `TBO_DATABASE_URL` (например `postgresql+psycopg://…`).
* **Контракт** — OpenAPI автоматически: `/docs`, `/openapi.json`. Это основа интеграции
  с другими модулями «Виртуального гаража» и с наземными станциями.

## Ключевое проектное решение: наработка вычисляется, а не хранится

Наработка **не хранится счётчиком, который можно испортить**. Она выводится из двух журналов,
в которые только добавляются записи:

* `flights` — факты эксплуатации из импортированных журналов (борт, взлёт, посадка, циклы);
* `installations` — интервалы «узел X стоял на борту Y в позиции P с … по …».

```
наработка_узла = начальная_наработка
               + Σ полётов f, для которых есть интервал установки i:
                   f.борт = i.борт и i.установлен ≤ f.взлёт < i.снят (или i.снят пуст)
```

Это даёт важные свойства:

| Ситуация | Результат |
|---|---|
| Узел переставлен на другой борт | Наработка остаётся за узлом и продолжает расти на новом борту — она привязана к экземпляру через интервалы |
| Журнал загружен *после* перестановки, а полёты были *до* неё | Часы уходят тому составу, который был на борту в момент взлёта (тест `test_late_import_uses_historical_configuration`) |
| Отмена ошибочного импорта | Удаляются полёты импорта — все счётчики (борт, узлы, регламенты) откатываются автоматически |
| Ретроспективная операция (дата в прошлом) | Уже загруженные полёты перераспределяются автоматически, ответ сообщает, сколько полётов затронуто |

Для отчётности в записи о ТО сохраняется снимок счётчиков на момент работы (`hours_at`, `cycles_at`).

## Модель данных

| Таблица | Назначение |
|---|---|
| `aircraft_types` | Тип БПЛА и его посадочные места (`slots`: позиция, название, тип узла) |
| `component_types` | Тип заменяемого узла (ПК, ИНС, ESC, БВК…) |
| `aircraft` | Паспорт борта: серийный номер, статус, базирование, начальный налёт |
| `components` | Паспорт узла: серийный номер, модель, ПО, статус, начальная наработка (стенд, другой парк) |
| `installations` | История установки/снятия: интервалы, основания, исполнители |
| `log_imports` | Журнал импортов: SHA-256 файла, статус, статистика, сообщения, сводка начислений |
| `flights` | Полёты; `UNIQUE(aircraft_id, external_id)` защищает от двойного начисления на уровне БД |
| `maintenance_rules` | Регламенты: объект, тип, вид (периодический / назначенный ресурс), интервалы и пороги предупреждения |
| `maintenance_records` | Выполненные работы по борту или узлу (с регламентом или внеплановые) |
| `settings` | Параметры калькулятора эффекта, якорь демо-данных |

Статусы борта: `active`, `maintenance`, `storage`, `retired`.
Статусы узла: `installed` (меняется только операциями установки/снятия), `stock`, `maintenance`, `retired`.

## Правила целостности при движении узлов

* узел устанавливается только в позицию своего типа, позиция должна быть свободна на дату операции;
* узел «на обслуживании» или списанный установить нельзя — сначала завершить обслуживание;
* интервалы установки одного узла и одной позиции не пересекаются (проверка + `CHECK` в БД);
* перестановка = снятие + установка в одной транзакции, атомарно;
* даты операций не могут быть в будущем и раньше ввода узла в эксплуатацию.

## Импорт журналов и защита от дублирования

1. **Уровень файла** — SHA-256 содержимого. Повторная загрузка уже обработанного файла (под любым именем)
   регистрируется в журнале импортов со статусом «Повтор — не начислено», счётчики не меняются.
2. **Уровень полёта** — ключ `(борт, flight_id)`; если ID нет, он строится детерминированно из
   борта и времени. Дополнительно — проверка **пересечения по времени** с уже учтёнными полётами того же
   борта: та же смена, выгруженная из другого источника с другими ID, не будет учтена дважды.
3. **Валидация строк**: неизвестный/списанный борт, посадка не позже взлёта, полёт в будущем, длительность > 24 ч,
   полёт до ввода борта в эксплуатацию. Ошибочные строки отклоняются, корректные импортируются (статус «частично»).
4. **Предпросмотр** (`dry_run`) — полный расчёт в транзакции с откатом.
5. **Отчёт импорта**: начисления по бортам и по каждому узлу, предупреждения (например, полёты при незаполненной позиции),
   сработавшие напоминания (сравнение состояния регламентов до и после импорта).

## Регламенты и напоминания

Регламент задаёт до трёх порогов — часы, циклы, календарные дни; срабатывает **первый достигнутый**.

* **Периодический** — отсчёт от последнего выполнения этой работы для данного экземпляра. Если работа
  не выполнялась — от ввода в эксплуатацию, с учётом всей наработки (консервативно). Выполнение работы
  обнуляет только этот интервал; сквозная наработка изделия не меняется.
* **Назначенный ресурс** — от начала эксплуатации, не обнуляется; по достижении — замена (система
  не даёт «закрыть» ресурс записью о работе).
* Статусы: «В норме» → «Приближается» (остаток ≤ порога предупреждения, по умолчанию 10 % интервала)
  → «Требуется / просрочено» (остаток ≤ 0).
* Прогноз даты — линейный, по средней интенсивности за 30 дней. Сложные модели отказов на этом этапе
  сознательно не применяются: все пороги прозрачны и проверяемы.
* Допуск борта к полётам = статус «В эксплуатации» + все позиции укомплектованы + нет просроченных работ
  ни по борту, ни по установленным узлам.

## Блок оценки эффекта

* **Предотвращённые пропуски ТО** — для каждого установленного узла считается состояние регламента
  двумя способами: поэкземплярно (фактически) и «как в формуляре борта» (только наработка с момента
  установки на текущий борт). Если фактически работа уже нужна, а «бортовой» учёт её не видит — это
  предотвращённый пропуск.
* **Скрытая наработка** — сквозная наработка узла минус наработка на текущем борту.
* **Калькулятор ₽** — прозрачные формулы с редактируемыми допущениями (вероятность отказа, ущерб,
  простой, трудозатраты на ручной учёт) поверх фактических показателей парка.

## Масштабирование и развитие

* Расчёт наработки — агрегирующие SQL-запросы по индексам `(aircraft_id, started_at)` и
  `(aircraft_id, installed_at, removed_at)`. Для парков в тысячи бортов: PostgreSQL + материализованные
  итоги, пересчитываемые по событиям (импорт, операция) — модель «журнал как источник истины» это позволяет без
  изменения логики.
* Импорт — синхронный; для больших потоков выносится в очередь (Celery/RQ) с тем же сервисом `import_log`.
* Мультиарендность (несколько эксплуатантов/сервисных организаций), роли и аудит пользователей,
  подпись записей о ТО — следующие этапы. Поле `operator` борта и `performed_by` работ уже заложены.
* Форматы журналов — подключаемые парсеры (`services/logs.py`): следующий шаг — прямой разбор
  журналов автопилотов (ArduPilot `.bin`, PX4 `.ulg`) и телеметрии собственных контроллеров заказчика.
