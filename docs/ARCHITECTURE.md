# Архитектура решения

## Обзор

```
 Браузер (SPA, vanilla JS)  ──HTTP/JSON──►  FastAPI (app/api/routes.py)
                                               │
                         ┌─────────────────────┼──────────────────────────┐
                         ▼                     ▼                          ▼
              services/inventory.py   services/logs.py         services/maintenance.py
              установка/снятие/        разбор журналов,         регламенты, остатки,
              перестановка             дедупликация, начисление список работ, выполнение,
                    ▲                  │   ▲                    уведомления
     services/movements.py ◄───────────┘   │ журнал полёта      ▲
     журналы движения узлов       services/sensors.py           │
     из Excel / PDF               падения / столкновения ───────┘
                                  по акселерометру
                         services/autopilot.py (api/missions.py): маршрут → симуляция полёта → журнал
                         services/drones.py ⇄ /api/agent ⇄ агент tbo-agent на борту (MAVROS → PX4) → журнал полёта
                         └──────────► services/usage.py ◄────────────────┘
                                      расчёт наработки (SQL)
                                               │
                                     SQLAlchemy 2 ORM → SQLite / PostgreSQL
```

* **Бэкенд** — FastAPI + SQLAlchemy 2. Бизнес-логика в `app/services/*`, HTTP-слой тонкий.
  Каждый изменяющий запрос — одна транзакция; нарушение бизнес-правила → `DomainError` → HTTP 4xx
  с понятным сообщением на русском.
* **Фронтенд** — одностраничное приложение без сборки и без внешних CDN, раздаётся тем же сервером
  и работает в закрытом контуре:
  - `app/static/index.html` — только каркас;
  - `css/*.css` — стили;
  - `js/*.js` — классические скрипты с общей областью видимости, по одному файлу на раздел, до ~300 строк.

  Встроенных скриптов и стилей нет — это нужно для строгой CSP.
* **Доступ** — `app/security.py` (правила по ролям, CSRF, заголовки) и `app/services/auth.py` (учётные записи, Argon2id,
  сессии, перебор, аудит). Подробно — [SECURITY.md](SECURITY.md).
* **Хранилище** — SQLite по умолчанию (ноль настройки) или PostgreSQL через `TBO_DATABASE_URL`. Пароль берётся из файла
  `TBO_DATABASE_PASSWORD_FILE`. Тесты проходят на обеих СУБД.
* **Контракт** — OpenAPI: `/docs`, `/openapi.json`. Включается `TBO_API_DOCS=1` и доступен только администратору.
  Это основа интеграции с другими модулями «Виртуального гаража» и с наземными станциями.

## Ключевое проектное решение: наработка вычисляется, а не хранится

Наработка **не хранится счётчиком, который можно испортить**. Она выводится из двух журналов,
в которые только добавляются записи:

* `flights` — факты эксплуатации из импортированных журналов (борт, взлёт, посадка, циклы);
* `installations` — интервалы «узел X стоял на борту Y в позиции P с … по …».

```
наработка_узла = начальная_наработка
               + Σ полётов f, для которых есть интервал установки i:
                   f.борт = i.борт и i.установлен ≤ f.взлёт < i.снят (или i.снят пуст)
```

Это даёт важные свойства:

| Ситуация | Результат |
|---|---|
| Узел переставлен на другой борт | Наработка остаётся за узлом и продолжает расти на новом борту — она привязана к экземпляру через интервалы |
| Журнал загружен *после* перестановки, а полёты были *до* неё | Часы уходят тому составу, который был на борту в момент взлёта (тест `test_late_import_uses_historical_configuration`) |
| Отмена ошибочного импорта | Удаляются полёты импорта — все счётчики (борт, узлы, регламенты) откатываются автоматически |
| Ретроспективная операция (дата в прошлом) | Уже загруженные полёты перераспределяются автоматически, ответ сообщает, сколько полётов затронуто |

Для отчётности в записи о ТО сохраняется снимок счётчиков на момент работы (`hours_at`, `cycles_at`).

## Модель данных

| Таблица | Назначение |
|---|---|
| `aircraft_types` | Тип БПЛА и его посадочные места (`slots`: позиция, название, тип узла) |
| `component_types` | Тип заменяемого узла (ПК, ИНС, ESC, БВК…) |
| `aircraft` | Паспорт борта: серийный номер, статус, базирование, начальный налёт |
| `components` | Паспорт узла: серийный номер, модель, ПО, статус, начальная наработка (стенд, другой парк) |
| `installations` | История установки/снятия: интервалы, основания, исполнители |
| `log_imports` | Журнал импортов: SHA-256 файла, статус, статистика, сообщения, сводка начислений |
| `flights` | Полёты; `UNIQUE(aircraft_id, external_id)` защищает от двойного начисления на уровне БД |
| `maintenance_rules` | Регламенты: объект, тип, вид (периодический / назначенный ресурс), интервалы и пороги предупреждения |
| `maintenance_records` | Выполненные работы по борту или узлу (с регламентом или внеплановые) |
| `settings` | Параметры калькулятора эффекта, якорь демо-данных |
| `component_usage_entries` | Наработка узла вне борта (стенд, формуляр, другой парк) |
| `sensor_events` | События датчиков: падение / столкновение, время, пиковая перегрузка, источник; принадлежат полёту |
| `movement_rows` | Ключи применённых строк журналов движения узлов (защита от повторной загрузки Excel/PDF) |
| `missions` | Миссия: точка взлёта, высота взлёта, скорость, RTL, точки маршрута (JSON) |
| `mission_runs` | Выполнения миссии: борт, итог, трек, сводка, ссылка на импорт журнала |
| `notification_events` | Журнал уведомлений сервера: ключ, категория, когда появилось и закрылось, доставка по каналам |
| `users` | Учётные записи: имя, роль, хеш пароля Argon2id, блокировка после неудачных входов, временный пароль |
| `auth_sessions` | Сессии: SHA-256 токена, CSRF-токен, срок, последняя активность, адрес и браузер |
| `audit_log` | Журнал аудита: входы, учётные записи, все изменяющие запросы к API (без паролей и тел запросов) |

Паспорт узла (`components`) дополнительно хранит неизменяемый `uid` (UUID), технические характеристики
`specs` (шаблон полей — `component_types.spec_fields`) и индивидуальный ресурс `resource_*`.

Статусы борта: `active`, `maintenance`, `storage`, `retired`.
Статусы узла: `installed` (меняется только операциями установки/снятия), `stock`, `maintenance`, `retired`.

## Правила целостности при движении узлов

* узел устанавливается только в позицию своего типа, позиция должна быть свободна на дату операции;
* узел «на обслуживании» или списанный установить нельзя — сначала завершить обслуживание;
* интервалы установки одного узла и одной позиции не пересекаются (проверка + `CHECK` в БД);
* перестановка = снятие + установка в одной транзакции, атомарно;
* даты операций не могут быть в будущем и раньше ввода узла в эксплуатацию.

## Импорт журналов и защита от дублирования

1. **Уровень файла** — SHA-256 содержимого. Повторная загрузка уже обработанного файла (под любым именем)
   регистрируется в журнале импортов со статусом «Повтор — не начислено», счётчики не меняются.
   Файл, в котором в прошлый раз были отклонённые строки, обрабатывается снова (после исправления данных
   применятся только они — уже учтённое отсекает уровень 2 и ключи строк журнала движения узлов).
2. **Уровень полёта** — ключ `(борт, flight_id)`; если ID нет, он строится детерминированно из
   борта и времени. Дополнительно — проверка **пересечения по времени** с уже учтёнными полётами того же
   борта: та же смена, выгруженная из другого источника с другими ID, не будет учтена дважды.
3. **Валидация строк**: неизвестный/списанный борт, посадка не позже взлёта, полёт в будущем, длительность > 24 ч,
   полёт до ввода борта в эксплуатацию. Ошибочные строки отклоняются, корректные импортируются (статус «частично»).
4. **Предпросмотр** (`dry_run`) — полный расчёт в транзакции с откатом.
5. **Отчёт импорта**: начисления по бортам и по каждому узлу, предупреждения (например, полёты при незаполненной позиции),
   сработавшие напоминания (сравнение состояния регламентов до и после импорта).

## Регламенты и напоминания

Регламент задаёт до трёх порогов — часы, циклы, календарные дни; срабатывает **первый достигнутый**.

* **Периодический** — отсчёт от последнего выполнения этой работы для данного экземпляра. Если работа
  не выполнялась — от ввода в эксплуатацию, с учётом всей наработки (консервативно). Выполнение работы
  обнуляет только этот интервал; сквозная наработка изделия не меняется.
* **Назначенный ресурс** — от начала эксплуатации, не обнуляется; по достижении — замена (система
  не даёт «закрыть» ресурс записью о работе).
* Статусы: «В норме» → «Приближается» (остаток ≤ порога предупреждения, по умолчанию 10 % интервала)
  → «Требуется / просрочено» (остаток ≤ 0).
* Прогноз даты — линейный, по средней интенсивности за 30 дней. Сложные модели отказов на этом этапе
  сознательно не применяются: все пороги прозрачны и проверяемы.
* Допуск борта к полётам = статус «В эксплуатации» + все позиции укомплектованы + нет просроченных работ
  ни по борту, ни по установленным узлам.

## Блок оценки эффекта

* **Предотвращённые пропуски ТО** — для каждого установленного узла считается состояние регламента
  двумя способами: поэкземплярно (фактически) и «как в формуляре борта» (только наработка с момента
  установки на текущий борт). Если фактически работа уже нужна, а «бортовой» учёт её не видит — это
  предотвращённый пропуск.
* **Скрытая наработка** — сквозная наработка узла минус наработка на текущем борту.
* **Калькулятор ₽** — прозрачные формулы с редактируемыми допущениями (вероятность отказа, ущерб,
  простой, трудозатраты на ручной учёт) поверх фактических показателей парка.

## Ручной ввод и внебортовая наработка

* **Ручной полёт** (`POST /api/flights`) проходит тот же конвейер, что и журнал: валидация, защита от
  дублей и пересечений, начисление борту и всем узлам, стоявшим на нём в момент взлёта, отчёт о сработавших
  напоминаниях. Технически это импорт с форматом `manual`, поэтому его можно удалить по одному
  (`DELETE /api/flights/{id}`), а полёты из журналов — только отменой импорта целиком.
  Если полёт вносится из карточки узла, система проверяет, что узел стоял на выбранном борту в момент взлёта.
* **Наработка вне борта** (`component_usage_entries`): стендовые прогоны, испытания, перенос из бумажного
  формуляра. Начисляется только узлу, участвует во всех его регламентах, в учёте «по борту» не видна.
  Стенд/испытания нельзя записать на период, когда узел стоял на борту (это был бы полёт борта);
  «корректировка по формуляру» допустима всегда.

## Индивидуальный ресурс экземпляра

У каждого борта и узла можно задать собственный максимальный износ — часы, циклы и/или дни (поля `resource_*`,
кнопка «⚙ Ресурс» в карточке, поля в формах создания). Он считается как назначенный ресурс: от начала эксплуатации,
выполнением работ не обнуляется, предупреждение — за 10 % до порога. В списке работ он показан как
«Индивидуальный ресурс (паспорт / формуляр)» и действует вместе с типовыми регламентами (срабатывает более строгий).
Базы прошлых версий получают новые столбцы автоматически при запуске (`app/db.py: migrate`).

## Справочники типов

Типы узлов и типы БПЛА с посадочными местами редактируются в интерфейсе («Узлы и склад» → «⊞ Свои типы узлов») и через API
(`/api/component-types`, `/api/aircraft-types`). Позиция может быть **обязательной** (без узла борт «некомплектен»
и не допущен) или **необязательной** (например, сменная полезная нагрузка). Защита целостности: нельзя удалить
позицию или сменить её тип, пока в ней стоит узел; нельзя удалить тип, на который ссылаются узлы, борта, позиции или регламенты.

## Генератор журналов

`app/loggen.py` — отдельный модуль с веб-интерфейсом («Генератор журналов», `POST /api/log-generator`) и CLI
(`python -m app.loggen`). Знает парк: не создаёт полёты в будущем, до ввода борта в эксплуатацию и (по умолчанию)
пересекающиеся с уже учтёнными. Для проверки защиты импорта может добавить дубликаты учтённых полётов и
ошибочные строки. Параметр `seed` делает генерацию воспроизводимой.

## Мониторинг датчиков

`services/sensors.py` выявляет падения (невесомость → удар) и столкновения (удар без невесомости) в выборке
акселерометра журнала полёта, принимает готовые события бортового ПО и счётчики из таблиц.
События хранятся за полётом (`ON DELETE CASCADE`) — откат импорта удаляет и их. Регламент может иметь интервал
«число событий» (`interval_events`): для борта считаются его события, для узла — события бортов за периоды,
когда узел на них стоял. Так ИНС, стоявшая на борту в момент удара, требует проверки, а узел со склада — нет.

## Журналы движения узлов из Excel / PDF

`services/movements.py` читает листы Excel (openpyxl) и таблицы PDF (pdfplumber), классифицирует таблицы
по заголовкам (журнал движения / журнал полётов) и применяет операции через `services/inventory.py`
в хронологическом порядке. Каждая строка — в своей точке сохранения (`SAVEPOINT`): ошибка не отменяет
остальные. Применённые строки запоминаются в `movement_rows`, поэтому PDF-копия Excel-журнала не задваивает
операции. Импорт движения не откатывается целиком — операции отменяются обратными операциями с узлами.

## Миссии и автономный полёт

`services/autopilot.py` — кинематический симулятор многороторного аппарата: взлёт, полёт по точкам
с алгоритмом следования по линии пути (pure pursuit + коррекция бокового отклонения), удержание, возврат (RTL),
посадка; ветер с порывами, ограничения ускорения и скорости набора/снижения. На выходе — трек, выборка
акселерометра и журнал `tbo-flightlog/1.0`, который проходит **штатный** импорт: наработка, датчики,
напоминания считаются так же, как для реального журнала. Перед вылетом `api/missions.py` выполняет
предполётную проверку допуска (статус, комплектность, нет просроченных работ и исчерпанного ресурса).
Экспорт/импорт QGroundControl `.plan` и `.waypoints` (MAVLink-команды 22/16/20) обеспечивает перенос миссии
на реальный автопилот; `scripts/run_mission_mavlink.py` — заготовка загрузки по MAVLink (pymavlink).

**Полёт на реальном борту** ([DRONE.md](DRONE.md)):
- **Агент `agent/tbo_agent`** работает на бортовом компьютере (ROS Noetic, MAVROS, PX4) и сам опрашивает
  `/api/agent/*` по токену устройства.
- **Серверная часть:**
  - `services/drones.py` — подключения, команды с коротким сроком жизни и приоритетом прерывания, сверка состояния
    борта, блокировка по борту;
  - `services/dronelog.py` — приём журнала полёта и **штатный** импорт: наработка, датчики, напоминания;
  - `api/drones.py` — команды оператора и подключение бортов.
- **Выполнения миссии** реального борта хранятся в тех же `mission_runs` (`source = drone`) с состояниями
  preparing → ready → in_flight → landed → completed | aborted.

## Уведомления

`GET /api/notifications` группирует результаты расчёта регламентов: «достигнут предельный ресурс»
(просрочен регламент вида «назначенный ресурс» или индивидуальный ресурс), «просрочено» (периодические работы),
«приближается» (остаток меньше порога предупреждения) и добавляет события датчиков за период.
Расчёт выполняется при каждом запросе по актуальным данным, поэтому уведомления появляются сразу после
импорта, полёта или операции и по календарю — без фоновых заданий. Интерфейс опрашивает сервис раз в минуту,
сравнивает с уже показанными позициями и выводит новые всплывающим сообщением и уведомлением браузера.

## Перестановка узлов перетаскиванием

`GET /api/board` отдаёт все борта с позициями, установленными узлами (паспорт, наработка, остаточный ресурс,
статус ТО) и узлы резерва/ремонта. Доска в интерфейсе выполняет перемещение теми же API операций
(`install` / `remove` / `transfer`); обмен узлами — последовательность «снятие → перестановка → установка»
с интервалом в секунду; время операции по умолчанию — не раньше предыдущей операции с этими узлами. После операции данные паспорта перечитываются и показываются «было → стало».

## Серверная модель

Вся бизнес-логика — на сервере; браузер — тонкий клиент (отображение и ввод):

| Что | Где выполняется |
|---|---|
| Наработка, остаточный ресурс, регламенты, допуск борта (`readiness`) | `services/usage.py`, `services/maintenance.py`, `api/routes.py` |
| Перестановка с доски: определение операции (установка / перестановка / замена / обмен / снятие), подбор времени, выполнение **одной транзакцией** | `services/board.py`, `POST /api/board/plan`, `POST /api/board/move` |
| Демо-сценарии 1–10 (возвращают блоки «до / после») | `services/scenarios.py`, `POST /api/scenarios/{n}/run` |
| Уведомления: журнал (появилось / закрыто / доставлено), проверка раз в минуту, рассылка в Telegram и на webhook | `services/notify.py`, `services/scheduler.py`, `GET /api/notifications/feed`, `/history` |
| Калькулятор эффекта, оценка маршрута миссии | `analytics.estimate`, `POST /api/analytics/estimate`, `POST /api/missions/estimate` |
| Резервные копии: логическая выгрузка таблиц в JSON + фото, zip (`tbo-backup/2`, не зависит от СУБД); восстановление одной транзакцией | `services/backup.py`, `/api/server/backups…` |
| Состояние сервера (модель Pi, температура, питание по `vcgencmd`, память, диск, адреса) | `services/sysinfo.py`, `GET /api/server/status` |
| Настройки сервера (каналы, расписание) — файл `server.json`, не затрагивается сбросом демо-данных и восстановлением | `services/serverconf.py` |
| Учётные записи (Argon2id), сессии, CSRF, роли, защита от перебора, первичная настройка по одноразовому коду, аудит | `services/auth.py`, `security.py`, `api/auth.py`, `main.py` |
| Командная строка администратора | `app/admin.py` (`python -m app.admin …`), обёртка `tbo-ctl` |

Фоновые задачи запускаются в том же процессе (asyncio + поток), поэтому сервис работает одним процессом uvicorn
(SQLite, единый планировщик). Развёртывание на Raspberry Pi 5 — `deploy/raspberry-pi/` и [RASPBERRY_PI.md](RASPBERRY_PI.md).

## Масштабирование и развитие

* Расчёт наработки — агрегирующие SQL-запросы по индексам `(aircraft_id, started_at)` и
  `(aircraft_id, installed_at, removed_at)`. Для парков в тысячи бортов: PostgreSQL + материализованные
  итоги, пересчитываемые по событиям (импорт, операция) — модель «журнал как источник истины» это позволяет без
  изменения логики.
* Импорт — синхронный; для больших потоков выносится в очередь (Celery/RQ) с тем же сервисом `import_log`.
* Мультиарендность (несколько эксплуатантов/сервисных организаций), роли и аудит пользователей,
  подпись записей о ТО — следующие этапы. Поле `operator` борта и `performed_by` работ уже заложены.
* Форматы журналов — подключаемые парсеры (`services/logs.py`): следующий шаг — прямой разбор
  журналов автопилотов (ArduPilot `.bin`, PX4 `.ulg`) и телеметрии собственных контроллеров заказчика.
